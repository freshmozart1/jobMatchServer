# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Node.js/Express backend that scrapes LinkedIn job postings, computes semantic embeddings (OpenAI `text-embedding-3-small`), ranks jobs by similarity to liked/disliked examples, and generates tailored cover letters via the `cover-letter-generator` package. See README.md for the full HTTP endpoint reference and request/response shapes; this file focuses on architecture that spans multiple files.

## Architecture

- **`src/index.ts` is a thin entrypoint** — it just calls `listenWithFallback()` and exits on failure. Routes and CORS live in `src/app.ts`: there are no separate router modules, every endpoint is wired directly on `app` in that file, alongside CORS handling and JSON body parsing. Port-binding/`EADDRINUSE`-retry logic (`listenWithFallback`) lives in `src/server/listen.ts`; graceful shutdown (signal handling, active-server tracking) lives in `src/server/shutdown.ts`. The token-service subprocess lifecycle lives in `src/tokenService/` (see below). Handler logic itself lives in `src/database/*.ts`, `src/scrapers/**`, `src/coverLetters/*.ts`, and `src/tokens/*.ts`.
- **Single MongoDB database (`jobMatch`), five collections**: `jobs`, `coverLetters`, `cv`, `certificates`, `users`. There is no auth/multi-tenancy — `getApplication.ts` reads a single hardcoded `USER_ID`. Each handler opens its own short-lived `MongoClient` (connect → operate → close in a `finally`); there's no shared/pooled client.
- **Job scoring pipeline** (`src/scrapers/linkedin/scrapeJob.ts` → `src/embeddings/jobEmbedding.ts` → `src/scrapers/linkedin/linkedInJobSimilarity.ts`): a scraped job is normalized, embedded, then scored against the average embedding of previously liked jobs (`like: true` docs) minus disliked ones, with liked/disliked embedding sets cached in-memory for 30s (`CACHE_TTL_MS` in `linkedInJobSimilarity.ts`) to avoid refetching on every job in a batch. `duplicateKey` is the dedupe key used to upsert on `POST /jobs/create`; `scrapeJob.ts` computes it as `linkedin:${sourceJobId}` (normalized-URL fallback) and checks MongoDB per job before streaming, skipping ones already stored. Client-disconnect detection in `scrapeJob.ts` must listen on `res.on('close', ...)`/`res.on('error', ...)`, not `req.on('close', ...)` — a request's `'close'` fires once its body is fully read (effectively immediately), which silently aborted every scrape until #117 fixed it.
- **Two-layer duplicate skipping in `scrapeJob.ts`** (#119/#131): before each `runScrape` call, `getStoredSourceJobIds` pre-fetches every stored `sourceJobId` into a `Set` once per request and builds a synchronous `shouldScrapeJob` predicate from it, passed to `linkedin-job-scraper` (`v0.13.0`) via `scraperOptions`. The scraper collapses duplicate list occurrences and normally checks this predicate once per distinct posting _before_ clicking into it; a deferred stale retry may check the same posting again. Jobs already known are skipped before the click/detail-pane-read/company-lookup (emitted as a `status: 'skipped'` `job:done` event, handled by a dedicated switch case in `handleProgressEvent`) instead of paying the full scrape cost and discarding the result afterward. Ordinary `runScrape` results therefore use contiguous logical indices and normally carry `duplicateOfIdx: null`. This pre-click filter is a best-effort optimization only — the pre-fetch runs after `res.writeHead` inside the client-disconnect `try`/`finally` so a failure doesn't delay the stream's first byte or leak the `MongoClient`, and a failed fetch just falls back to an empty `Set` (scrape everything, pre-#119 behavior) rather than aborting the request. The existing post-scrape `duplicateKey` check above remains the correctness safety net: it's the only check that runs for jobs with no `sourceJobId` (matched by normalized URL instead) and for any job the pre-click filter missed because the pre-fetch itself failed.
- **LinkedIn detail-pane identity gate and overlay diagnostics** (#126): `linkedin-job-scraper` v0.13.0 only returns a successful result after the detail title-link's parsed posting ID exactly matches the clicked card's `sourceJobId`. A persistent mismatch becomes `status: 'failed'` with `failureReason: 'detail-pane-identity-unverified'` and remains eligible for the package's single deferred retry; `handleProgressEvent` logs that failure but never sends it through dedupe, embedding, matching, or a job frame. The handler exhaustively consumes the package's progress union. `overlay:undismissed` is logged with the package's length-capped `describeOverlayDiagnostics` rendering. Do not serialize whole upstream progress events or job diagnostics: v0.13.0 can attach diagnostic records containing optional DOM snapshots.
- **`POST /scrape/linkedin`'s request-body validation** (#143): `src/utils/getLinkedInJobScraperSearchParamsFromBody.ts` is the only validator for this route, and `location` is the one field it treats as **optional** — absent, `undefined`, and blank-after-trim all mean "no location", and the key is then left off the returned object entirely rather than set to `''`. `scrapeJob.ts` spreads it conditionally into `runScrape`'s `searchParams` for that reason: `linkedin-job-scraper`'s `buildSearchUrl` omits the query param only when the field is `undefined`, so passing `''` would put an empty `location=` on the LinkedIn URL. Requiring it here was the outlier that broke first-run scrapes, since the jobMatch UI labels the field "Location (optional)" and sends `''` when blank. A non-string, non-`undefined` `location` is still rejected (`isValidLocation`), so garbage keeps producing a `400` instead of being silently coerced away. The `400` body keeps the bare `{ error }` shape the UI reads — not `createErrorMessage`'s `{ message, error }` — but carries the exported `INVALID_BODY_ERROR_MESSAGE`, which names every field; the test imports that constant rather than copying the string. `distance` is still required and still sent even with no location to centre it on (tracked as #148).
- **`POST /scrape/linkedin`'s SSE frame contract** (#122/#124/#131): every JSON `data:` value is a `ScrapeStreamFrame` discriminated by `type`: `{ type: 'job', job }`, keyword-tagged loading/scanning progress, or `{ type: 'error', error, reason, keyword? }`. `jobs:loading` reports the distinct-posting count as `discovered`; `jobs:found` reports the final distinct-posting total with `current: 0`; `job:start` uses the scraper's contiguous zero-based logical index and is converted to a one-based `current`. Failed/dropped counts are maintained per keyword by job index and reflect the latest terminal result, so deferred retries overwrite rather than double-count and a success/skip clears a prior failure. The stream opens with `: ping\n\n` to flush headers and writes `: keepalive\n\n` every 15 seconds; comments and JSON frames all go through `writeIfConnected`, and the interval is cleared on completion or disconnect. A run-level error's `reason` is built by `describeFailureReason` — **only a message ever goes on the wire, never the error object**: an `Error`'s own fields are non-enumerable, while spreading it would leak internal state (`ScrapeAbortedError` carries the partial results array). Preserve the `message || name`, error-like `message`, and guarded `String()` fallbacks so malformed rejection values cannot strand the stream open.
- **Cover letter pipeline** spans three endpoints and delegates segmentation, embedding, ranking, generation, and selected-text revision entirely to the `cover-letter-generator` package — jobMatchServer's own code is limited to MongoDB access, the Express layer, and `StoredCoverLetter` <-> package-type adapters. `POST /cover-letters/upload/text` (`src/database/uploadCoverLetterAsText.ts`) stores letters _segmented_ (`subject`/`salutation`/`introduction`/`mainBody`/`conclusion`/`greetings`, see `CoverLetterSegmentName` in `src/types.ts`), each with its own embedding: `segmentCoverLetter` (heuristic first, LLM fallback) and `embedCoverLetterSegments` do the actual work, with local `toStoredCoverLetter`/`toStoredCoverLetterSegment` adapters converting the package's `CoverLetter` type to this repo's stored shape. Both model calls finish before the handler connects: its only database work (upsert by `jobDuplicateKey`, else insert) runs in the unexported `storeCoverLetter` helper, which connects, writes, and closes in its own `finally`, so no connection idles through segmentation or embedding, and the `201` goes out only after the client has closed. Tests pin that embedding settles before `connect()` and that a model failure never connects — don't move `connect()` back above the model calls. The client is still _constructed_ before them, so a malformed connection string still throws before any model spend. `POST /cover-letters/create/text` (`src/coverLetters/generateCoverLettersAsText.ts`) fetches every stored cover letter, converts it to the package's shape via `src/coverLetters/coverLetterAdapters.ts` (`toGeneratorCoverLetter`, `getGeneratorCoverLetterTextSegments`), then hands ranking and generation to the package in one round trip: `embedJob` embeds the target job, `getTopXSimilarCoverLetters` ranks stored letters against it by a fixed per-segment weighting (`mainBody` dominant) rather than a single whole-letter embedding, and `generateCoverLetter` writes the new letter from the top `x` matches (default 3). `POST /cover-letters/revise/text` (`src/coverLetters/reviseCoverLetterAsText.ts`) is stateless: it validates that the exact selected passage occurs in the supplied complete draft, calls the package's `reviseCoverLetterText`, and returns only the replacement without touching MongoDB. There is no `getTopXSimilarCoverLetters.ts` in this repo anymore — ranking is no longer a separate endpoint or local module, and the weighting itself lives in the package, not here.
- **Cover-letter create and revise sanitize provider errors identically** (#133/#135): `cover-letter-generator` v0.11.0 rejects a Responses API result with `status: 'incomplete'` by throwing a descriptive `Error` naming the incomplete reason, instead of handing the truncated payload to `JSON.parse` and surfacing a bare `SyntaxError`. Both routes catch it, log it, and answer `500` through `createErrorMessage` (`src/errors/createErrorMessage.ts`), and both pass the explicit literal `'Provider request failed'` as its `publicError` argument — `POST /cover-letters/revise/text` (`reviseCoverLetterAsText.ts`) from the start, `POST /cover-letters/create/text` (`generateCoverLettersAsText.ts`) since #135. The provider's message, including v0.11.0's descriptive incomplete-response error, stays server-side in the `console.error` log; the body keeps `createErrorMessage`'s `{ message, error }` shape. Before #135 the create route let `publicError` default to the caught error, which put raw `OpenAI.APIError` text (organization/project identifiers, request IDs, quota detail) in the body of an unauthenticated endpoint. The two call sites must stay identical, and both route test files pin the wire string. The create route's single `try` also wraps MongoDB `connect()`/`find().toArray()`, so a database failure gets the same `'Provider request failed'` string — accepted deliberately, and pinned by that route's tests, which reject each awaited call in turn. `createErrorMessage`'s `publicError` still defaults to the raw error at every other call site, including `POST /cover-letters/upload/text` (`src/database/uploadCoverLetterAsText.ts`), which forwards raw OpenAI errors from `segmentCoverLetter`'s LLM fallback and `embedCoverLetterSegments` (tracked in #155); any new call site that catches provider or driver errors must pass an explicit `publicError`. Generation and revision both run `gpt-6-astra` at `reasoning.effort: 'high'` from package-internal constants shared by both functions, so those two cannot drift; segmentation's LLM fallback model is a separate constant and is unchanged.
- **Token counting is a Python sidecar**, not a Node library: `src/tokenService/tokenService.py` (Flask + `tiktoken`) is spawned lazily on first request by `ensureTokenServiceStarted()` in `src/tokenService/startTokenService.ts`, which picks its own free port, prints `TOKEN_SERVICE_URL=http://...` on stdout, and is parsed line-by-line to learn the URL (stashed in `process.env['TOKEN_SERVICE_URL']`, consumed by `src/tokens/fetchTokens.ts`). `tokenService.py` is the only non-TypeScript file in that directory — `tsc` never picks it up (it only compiles `.ts`), and ESLint/nodemon watch it like any other file in `src` now that the rest of `src/tokenService/` is real TypeScript. Python binary resolution order: `PYTHON` env var → `.venv/bin/python` → interpreter behind `pip`/`pip3` on `PATH` → `python3` (`resolvePythonBinary()` in `src/tokenService/resolvePythonBinary.ts`).
- **Application PDF assembly** (`getApplication.ts`): the stored cover letter is rendered from `src/database/coverLetter.html` (a `{{placeholder}}` template, copied to `dist/` by the build step) to PDF via headless Puppeteer, then merged with the stored CV and any certificates (PDF/JPEG/PNG) into one PDF via `pdf-lib`. A malformed certificate is skipped, not fatal, to the merge.
- **Uploaded-file path safety**: `src/utils/isPathInside.ts` gates every filesystem read derived from a DB-stored `filePath` (CV, certificates) before `path.resolve()`/`readFile` — required because `getApplication.ts` and `getCV.ts` trust paths coming out of MongoDB, not directly off the request.
- **`// fallow-ignore-file security-sink` header comments** appear on a few files (`src/app.ts` for the CORS sink, `src/tokenService/startTokenService.ts` for the spawn sink, `getApplication.ts`, `isPathInside.ts`, `fetchTokens.ts`). These are dated, reasoned suppressions of the `fallow` static analyzer's security-sink rule (e.g. "this `fetch()` target is a locally-spawned sidecar URL, never attacker input"), not dead comments — don't strip them without re-verifying the claim still holds, and add an equivalent comment if you introduce a new sink that needs the same treatment.
- **Test mocking**: `src/testMockModules/*.test.ts` hold reusable `jest.unstable_mockModule()` factories (e.g. `mongodb.test.ts` mocks `MongoClient`/`ObjectId`) imported by multiple `*.test.ts` files, so a MongoDB/embeddings/segmentation mock is defined once and shared rather than duplicated per test file.

## Build & test

```bash
npm run build        # tsc + copies src/database/coverLetter.html → dist/
npm start            # runs the built server (dist/index.js), loading .env if present
npm run dev          # concurrently starts mongod, waits for it, then nodemon (ts-node ESM loader)
npm run test:once    # build then run Jest once — use this, not `npm run test` which loops forever
npm run lint         # eslint .
npm run format       # prettier --write .
npm run mongo        # starts a local mongod using the homebrew dbpath (also run automatically by `npm run dev`)
```

To run a single test file:

```bash
node --experimental-vm-modules --localstorage-file=/tmp/jest-localstorage.json ./node_modules/jest/bin/jest.js --config jest.config.mjs --runInBand dist/path/to/file.test.js
```

## Testing

- **Always build before running Jest** — tests run against compiled output in `dist/`, not source TypeScript.
- ESM mocking uses `jest.unstable_mockModule()` — mock setup must precede the module-under-test import, which must use dynamic `await import(...)`.
- `testHelpers/` and `testMockModules/` hold shared utilities named `*.test.ts`; they are excluded from test suites via `testPathIgnorePatterns`, not `testMatch`.
- `--runInBand` is required (already set in config) — tests run serially to avoid Puppeteer/MongoDB conflicts.

## TypeScript conventions

- `"moduleResolution": "nodenext"` — **all local imports must end in `.js`**, even in `.ts` source (e.g., `import foo from './foo.js'`).
- `verbatimModuleSyntax: true` — use `import type` for type-only imports.
- `noUncheckedIndexedAccess: true` — array/object index access returns `T | undefined`.
- `exactOptionalPropertyTypes: true` — optional properties cannot be explicitly assigned `undefined` unless `undefined` is in their type.
- Path aliases (`#scrapers/*`, `#database/*`, `#types`, `#index`, `#utils/*`) are defined in **both** `package.json` `imports` and `tsconfig.json` `paths` — update both when adding a new alias.

## Required environment variables

| Variable                    | Notes                                                                                                                                                                                                                                                            |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MONGODB_CONNECTION_STRING` | MongoDB connection URI; checked at startup and before every DB call                                                                                                                                                                                              |
| `OPENAI_API_KEY`            | Picked up automatically by the OpenAI SDK; no explicit reference in source. Also now required at process startup, not just call time — `cover-letter-generator`'s `dist/llm.js` constructs an OpenAI client at import time, and `src/app.ts` imports it eagerly. |
| `PYTHON`                    | Optional; overrides Python binary resolution for the token-service subprocess                                                                                                                                                                                    |

Copy `.env.example` to `.env` and fill in the values to configure these locally — `npm run dev` and `npm start` both load it automatically via Node's `--env-file-if-exists` flag if present. Variables already set in the shell or by a process manager take precedence over `.env` values.

## Git / GitHub flow

Follow [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow) for all changes:

1. **Create a branch** off `master` — short, descriptive name with a prefix: `feat/...`, `fix/...`, `refactor/...`, `docs/...`. Folding the issue number in is common in this repo, e.g. `docs/issue-66-update-readme`.
2. **Make changes** — keep each commit isolated and complete (e.g. don't mix an unrelated rename into a commit adding tests) so it can be reverted independently. Use a conventional commit message: `type: short description`, adding `(closes #N)` when the commit closes an issue.
3. **Open a pull request** against `master` — summarize what changed and why. Open it as a **draft** if you want early feedback before it's ready for review.
4. **Address review comments** — push additional commits to the same branch; the pull request updates automatically.
5. **Wait for CI, then merge** — `.github/workflows/test.yml` runs `npm run test:once` (against a real MongoDB service container) on every push and pull request; don't merge until it's green. This repo's history is entirely merge commits (`Merge pull request #N from ...`), not squashes — match that unless told otherwise.
6. **Delete the branch** after it's merged.
